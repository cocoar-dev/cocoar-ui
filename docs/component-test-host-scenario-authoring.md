# Component Test Host — Scenario Authoring Guide

This document explains how to write a scenario definition today:

- how scenario discovery works
- how query parameter parsing works
- how to override parsing for individual inputs
- how to provide custom parsers

This is intentionally practical and matches the current implementation.

---

## Mental Model

- A **scenario component** is an Angular component that renders a scenario in isolation (often a wrapper around the real design-system component).
- The host mounts one scenario at a time at `/__scenario/:id`.
- Inputs are configured via URL query params and applied to the scenario component using `componentRef.setInput()`.

---

## Where To Put Scenarios

Within the CT host app, scenarios typically live under:

- `apps/component-test-host/src/app/scenario/scenarios/**`

A scenario usually has:

- `my-scenario.component.ts` (+ html/css)
- `my-scenario.scenario.ts` (metadata)

The registry is auto-generated by scanning the configured search roots (see `scenar-backstage.config.json`).

---

## The `ScenarioDefinition` Type

`ScenarioDefinition` is defined in `apps/component-test-host/src/app/scenario/scenario-types.ts`.

A minimal scenario metadata object looks like:

```ts
import type { ScenarioDefinition } from '../../scenario-types';
import type { MyScenarioComponent } from './my-scenario.component';

export const myScenario: ScenarioDefinition<MyScenarioComponent> = {
  id: 'my-scenario-id',
};
```

Notes:

- The `id` becomes the URL segment: `/__scenario/my-scenario-id`.
- The `id` becomes the URL segment: `/__scenario/my-scenario-id`.
- The generic type (`ScenarioDefinition<MyScenarioComponent>`) is used by the generator to find the component class.
- IDs are set manually and must be **globally unique** within the repository. The registry generator fails if duplicate IDs are detected.

## How Query Param Parsing Works

### 1) Only allowlisted inputs are read

At runtime, the host reads query params and applies them only for allowlisted inputs defined on the registry entry.

Implementation: `apps/component-test-host/src/app/scenario/scenario-host.page.ts`.

### 2) Each input has a parser

A parser has type:

```ts
export type ScenarioInputParser = (raw: string) => unknown | ScenarioSkip;
```

If a parser returns `SCENARIO_SKIP`, the value is ignored (no input is set).

This is the default behavior for invalid values: we **ignore invalid query parameter values** rather than throwing.

Implementation: `apps/component-test-host/src/app/scenario/scenario-parsers.ts`.

### 3) Only the first query param value is used

Angular `ParamMap.get(name)` returns the first value.

So this URL:

- `?disabled=true&disabled=false`

will pass only the first value (`true`) to the parser.

---

## Parser Helpers (Built In)

These helpers exist in `apps/component-test-host/src/app/scenario/scenario-parsers.ts`.

### `scenarioParseBoolean(raw)`

- Accepts common “truthy” values: `true`, `1`, `yes`, `on`
- Special case: empty string means `true`
  - so `?disabled` will be treated as `disabled=true`

### `scenarioParseNumber(raw)`

- `''` (empty) → `SCENARIO_SKIP`
- non-finite / NaN → `SCENARIO_SKIP`
- otherwise returns a `number`

### `scenarioParseString(raw)`

- returns the string as-is

### `scenarioParseEnum(['a','b'])`

- if `raw` is in the allowlist → returns `raw`
- otherwise → `SCENARIO_SKIP`

## Auto-Inferred Inputs (Most Common Case)

The registry generator auto-infers an allowlist of inputs by scanning the scenario component class for signal inputs declared using Angular’s `input()` API.

Example scenario component:

```ts
import { Component, input } from '@angular/core';

@Component({
  standalone: true,
  template: `...`,
})
export class MyScenarioComponent {
  disabled = input(false);
  label = input<string>('Hello');
  size = input<'sm' | 'md' | 'lg'>('md');
  count = input<number>(0);
}
```

What this means:

- `disabled` → boolean parser
- `label` → string parser
- `size` → enum parser (for small string-literal unions)
- `count` → number parser

The generator currently:

- detects `input(...)` and `input.required(...)`
- supports: `boolean`, `number`, `string`, and small string-literal unions (max 50) for enums
- falls back to string parsing for unknown/complex types

## Overriding Parsing For A Single Input

You can override inferred parsers by adding an exported scenario definition in a `*.scenario.ts` file.

Important constraint:

- overrides are only applied when the scenario metadata is:
  - **exported**, and
  - defined in a `*.scenario.ts` file

Reason: the generated registry only imports metadata from `*.scenario.ts` to avoid eager-loading scenario chunks.

### Example: override one input

```ts
import { SCENARIO_SKIP, scenarioParseEnum, scenarioParseString } from '../../scenario-parsers';
import type { ScenarioDefinition } from '../../scenario-types';
import type { MyScenarioComponent } from './my-scenario.component';

export const myScenario: ScenarioDefinition<MyScenarioComponent> = {
  id: 'my-scenario-id',
  inputs: {
    // override inferred string parsing
    label: (raw) => scenarioParseString(raw).trim(),

    // replace inferred enum with a stricter allowlist
    size: scenarioParseEnum(['sm', 'md']),

    // completely disallow an input from query params
    count: false,

    // custom parser that can skip invalid values
    mode: (raw) => (raw === 'auto' || raw === 'manual' ? raw : SCENARIO_SKIP),
  },
};
```

Semantics:

- omitted key → use inferred parser
- `ScenarioInputParser` → override inferred parser
- `false` → remove this input from the allowlist

## Adding Providers (Per Scenario)

If a scenario needs providers (overlays, stubs, test doubles), add them on the scenario metadata (same export constraint as above):

```ts
import type { ScenarioDefinition } from '../../scenario-types';
import type { MyScenarioComponent } from './my-scenario.component';
import { provideNoopAnimations } from '@angular/platform-browser/animations';

export const myScenario: ScenarioDefinition<MyScenarioComponent> = {
  id: 'my-scenario-id',
  providers: [provideNoopAnimations()],
};
```

## Writing Custom Parsers (Guidelines)

A custom parser should:

- accept a single string
- return a value compatible with the scenario input
- return `SCENARIO_SKIP` for invalid input

Examples:

### Comma-separated string list

```ts
import { SCENARIO_SKIP } from '../../scenario-parsers';

export function parseStringList(raw: string) {
  const normalized = raw.trim();
  if (normalized === '') return SCENARIO_SKIP;
  return normalized
    .split(',')
    .map((s) => s.trim())
    .filter(Boolean);
}
```

### Strict JSON parser (careful)

```ts
import { SCENARIO_SKIP } from '../../scenario-parsers';

export function parseJson(raw: string) {
  try {
    return JSON.parse(raw);
  } catch {
    return SCENARIO_SKIP;
  }
}
```

Recommendation: keep parsers small and deterministic. Prefer query params that are easy to read and debug.

## Troubleshooting

### “My overrides are ignored”

Check:

- scenario metadata is `export const ...`
- file name ends with `*.scenario.ts`

If the scenario is declared only in a `*.component.ts`, the generator can discover the `id` but cannot import overrides without eager-loading.

### “My param is not applied”

Common reasons:

- not part of the allowlist (no `input()` field and no override)
- parser returned `SCENARIO_SKIP` because the value was invalid
- key name mismatch (query param name must match the input name exactly)
